# 실시간 60fps 목표 달성 가능성 분석

- **ID**: 001
- **날짜**: 2026-04-28
- **유형**: 분석 문서

## 작업 요약
현재 실시간 파이프라인의 FPS 의미를 클라이언트 렌더링, 브라우저 포즈 추정, 서버 AI 추론으로 분리해 재해석했다. 결론적으로 현 구조에서 "AI 전체 파이프라인 60fps"는 비현실적이며, 운영 목표는 **화면 표시 FPS**와 **AI 추론 샘플링 FPS**를 분리해서 잡아야 한다.

## 기존 근거 정리
1. **브라우저 포즈 오버레이**
   - `page.dashboard/view.ts`에서 MediaPipe 루프는 `MP_FRAME_INTERVAL_MS = 83`으로 약 12fps로 스로틀되어 있다.
   - 2026-04-03 최적화 이력에서 Heavy→Lite 전환, 60fps→12fps 스로틀이 핵심 개선안이었다.
   - 즉, 현재 11~12fps는 "의도적으로 제한한 브라우저 포즈 추정 FPS"에 가깝다.

2. **서버 실시간 낙상 추론**
   - 2026-03-27 검토 이력 기준 640x480 webm 4초 청크의 서버 분석 시간은 약 0.42초, 전체 요청은 약 0.898초였다.
   - 이후 2026-04-13 RF-Dual은 3초 청크 / 1.5초 간격 / YOLO single-pass로 최적화되었다.
   - 서버 추론은 원본 30~60fps를 그대로 다 쓰지 않고, realtime target_fps 3 / max 12프레임 수준으로 축소 샘플링한다.

3. **병목 구조**
   - 기존 최적화 이력에서 가장 큰 병목은 프레임 추출/디코딩이었다.
   - YOLO single-pass, 모델 캐시, imgsz 축소로 줄였지만, 전체 파이프라인을 60fps로 밀어 올리려면 디코딩·추론·후처리 전체가 선형에 가깝게 증가한다.

## 분석 결론
### 1. 60fps 달성 가능성 평가
| 대상 | 현재 상태 | 60fps 목표 | 판단 |
|------|-----------|------------|------|
| UI 비디오 표시 | 브라우저 기본 렌더링으로 가능 | 가능 | 상 |
| 브라우저 오버레이(MediaPipe) | 약 11~12fps | 60fps 상시 분석은 과부하 위험 큼 | 하 |
| 서버 AI 추론(RF-Dual) | 3fps 샘플링 기반 | 60fps 원프레임 분석은 구조상 부적합 | 하 |
| 부분 최적화 후 체감 반응성 | 1.5~3초 단위 갱신 | 충분히 개선 가능 | 중상 |

### 2. 현실적인 운영 목표
- **UI 렌더링 FPS**: 30~60fps
- **브라우저 포즈 오버레이**: 12~20fps
- **서버 AI 추론 샘플링**: 3~8fps
- **고성능 GPU + 추론 엔진 최적화 시 상한**: 15~30fps 상당의 분석 파이프라인 가능성
- **현 구조 유지 시 현실적 상한**: 15~25fps 수준의 부분 경량화, 또는 현재처럼 3~8fps 샘플링 + 빠른 갱신 주기 유지

## 과부하 예측
### 1. 브라우저 측
- MediaPipe를 12fps에서 60fps로 올리면 추론 호출 수가 약 5배 증가한다.
- 예상 영향:
  - 노트북/내장 GPU: 발열 상승, 프레임 드랍, 팬 소음 증가
  - 저사양 기기: UI 입력 지연, 캔버스 렌더링 끊김
  - 장시간 구동: thermal throttling 가능성

### 2. 서버 측
- 현재 realtime target_fps 3 기준인데 이를 30~60fps로 올리면 처리 프레임 수가 약 10~20배 증가한다.
- 예상 영향:
  - 큐 적체 및 청크 지연 누적
  - YOLO 추론 시간 선형 증가
  - 메모리 사용량 증가
  - 실시간 판단보다 "분석 대기" 상태가 길어질 가능성

## 즉시 가능한 개선
1. MediaPipe 오버레이를 **12→15~20fps** 범위에서 점진 실험
2. 캔버스 draw 비용, DOM 갱신 빈도, `service.render()` 호출 타이밍 점검
3. 서버는 현행 3fps 샘플링을 유지하되, threshold/guard와 분리해서 **청크 생성 주기 체감 개선** 우선
4. 낮은 해상도 경로(예: 320~480px)와 높은 해상도 경로를 분리

## 구조 개편이 필요한 개선
1. ONNX / TensorRT / OpenVINO 등 추론 엔진 전환
2. detect/pose/분류 파이프라인 비동기 분리
3. 브라우저 경량 오버레이와 서버 정확도 추론의 이원화
4. GPU 전용 배포 프로파일 분리

## 권장안
- **운영 KPI를 60fps로 두지 말고**,
  - "UI는 60fps에 가깝게 부드럽게 표시"
  - "AI 판단은 1~2초 이내에 안정적으로 갱신"
  로 분리하는 것이 맞다.
- 현재 프로젝트의 우선순위는 60fps 자체보다 **오탐/미탐 개선 + 체감 지연 감소**가 더 높다.

## 최종 판단
- **즉시 적용 가능**: 부분 가능
- **예상 성능**: 현 구조 기준 15~25fps 수준의 부분 개선 여지, 운영형 AI 분석은 3~8fps 샘플링이 가장 합리적
- **60fps 전체 AI 파이프라인**: 현 시점에서는 보류가 타당
