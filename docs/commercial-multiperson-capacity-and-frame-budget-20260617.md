# 상용 환경 다중 인원 처리 및 프레임 예산 보고서

작성일: 2026-06-17

## 1. 현재 결론

현재 시스템은 스켈레톤 표시와 분석 결과 표시에서 최대 20명까지 사람 라벨을 붙일 수 있도록 확장했습니다. 다만 낙상 판정 모델은 아직 대표 1명을 중심으로 판단하는 구조이므로, 상용화에서 즉시 보증 가능한 판정 인원은 1명, 보호자나 간병인이 같이 들어오는 통제 환경까지 포함하면 2명입니다.

20명까지의 다중 인원은 "화면 표시와 추적 보조"는 가능하지만, 각 사람별 독립 낙상 판정을 완전히 보증하려면 track_id별 시계열 분리, 사람별 모델 입력, 사람별 알림 병합 정책까지 운영 경로에 통합해야 합니다.

## 2. 현재 구현 상태

### 브라우저 스켈레톤 모드

- MediaPipe Pose Landmarker `numPoses=20` 기준으로 최대 20명 스켈레톤을 표시합니다.
- 각 사람은 화면상 `P1`부터 색상으로 구분됩니다.
- 2026-06-17 수정으로 브라우저 skeleton 모드에도 중심점 거리 기반 track id를 붙였습니다.
- 이 track id는 실시간 화면에서 짧은 가림/누락을 견디기 위한 표시용입니다. 사람이 장시간 교차하거나 서로 겹치면 ID switch 가능성이 남습니다.

### 서버 분석 결과

- 서버의 `detection_frames`는 최대 5명까지 bbox, keypoints, confidence, label을 반환합니다.
- 2026-06-17 수정으로 분석 chunk 내부에서는 bbox IoU와 중심점 거리 기반의 `track_id`를 붙입니다.
- 이 `track_id`는 chunk-local입니다. 긴 영상 전체나 실시간 세션 전체에서 ID를 영구 유지하려면 track tail cache를 세션 상태로 보존해야 합니다.

### 실제 낙상 판정

- 현재 RF-Fall/RF-Dual 판정 입력은 대표 1명의 시계열을 기준으로 합니다.
- 여러 명이 있으면 가장 큰 bbox의 대표 인원이 우선 선택됩니다.
- 따라서 현재 운영판에서는 "여러 명을 화면에 표시"와 "여러 명 각각을 독립 판정"을 구분해야 합니다.

## 3. 인원 수별 성능 검토

측정 스크립트: `scripts/benchmark_multiperson_frame_processing.py`

측정 조건: YOLOv8n-pose, sample-fall 영상을 타일링한 합성 다중 인원 입력, 서버 CPU 환경 기준. 20명 확장 테스트는 `outputs/performance/multiperson_frame_benchmark_20_640.json`에 저장했습니다.

| 인원 | 처리 FPS | 프레임 RTT | 평균 검출 인원 | 판정/운영 해석 |
|---:|---:|---:|---:|---|
| 1명 | 42.4 | 0.189초 | 1.25 | 즉시 운영 가능 |
| 2명 | 33.0 | 0.242초 | 2.75 | 통제 환경 운영 가능, 약한 과검출 |
| 5명 | 48.3 | 0.166초 | 7.75 | 표시 가능, 과검출 억제 필요 |
| 10명 | 52.5 | 0.152초 | 6.50 | 일부 누락 발생, 판정 신뢰 하락 |
| 14명 | 52.2 | 0.153초 | 14.75 | RTT 예산 내, 실제 ID 유지율 검증 필요 |
| 20명 | 43.1 | 0.186초 | 24.12 | 처리량 한계 테스트, 과검출/ID switch 리스크 큼 |

주의: 위 수치는 pose 검출 처리량 검토입니다. “인원이 많아져도 성능 저하가 없다”는 결론이 아니라, 합성 pose-only 조건에서 RTT/처리량 예산을 넘지 않았다는 의미입니다. 실제 낙상 정확도는 사람별 라벨이 있는 다중 인원 낙상 데이터가 있어야 별도로 검증할 수 있습니다.

## 4. 상용화에서 통제 가능한 인원수

| 단계 | 권장 인원 | 근거 |
|---|---:|---|
| 현재 운영판 낙상 판정 보증 | 1명 | 대표 인원 1명 시계열 기준 |
| 현재 통제 환경 | 2명 | 대상자 1명 + 보호자/간병인 1명까지는 대표 대상 유지가 비교적 쉬움 |
| 실시간 기본 무저하 테스트 | 3명 | 2026-06-25 재측정에서 RTT와 검출 안정성을 함께 유지한 상한 |
| 현재 화면 표시/검토 | 20명 | 스켈레톤 표시 제한을 20명으로 확장 |
| 추적 통합 후 목표 | 5명 | track_id별 시계열 분리와 사람별 알림 정책 필요 |
| 연구/시연 한계 테스트 | 20명 | 처리량 확인용, 상용 판정 보증 아님 |
| 5명 초과 | 비권장 | 카메라 분리, ROI 구역 분리, 병실/침대별 카메라 분리가 더 안정적 |

상용 환경에서는 카메라 1대당 판정 대상 5명을 hard limit으로 두고, 화면 표시만 최대 20명까지 허용하는 구조가 안전합니다. 다만 2026-06-25 재측정 기준으로 “성능 저하 없음”이라고 말할 수 있는 실시간 기본 상한은 3명입니다. 실제 낙상 알림 보증은 사람별 추적 판정 통합이 끝날 때까지 1-2명 환경으로 제한하는 것이 안전합니다.

## 5. 최적 프레임 수

현재 낙상 분석 chunk는 4초 구간 기준 4fps, 즉 16프레임을 기본값으로 두는 것이 가장 균형이 좋습니다.

| 운영 모드 | 권장 설정 | 설명 |
|---|---:|---|
| 기본 실시간 분석 | 4초 x 4fps = 16프레임 | 정확도와 지연의 균형 |
| CPU 부족 또는 4-5명 밀집 | 4초 x 3fps = 12프레임 | RTT 안정화 우선 |
| 낙상 위험 구역 | 4초 x 5fps = 20프레임 | 움직임 변화 포착 강화 |
| GPU/엣지 여유 장비 | 4초 x 6fps = 24프레임 | 상한 권장 |
| 24프레임 초과 | 비권장 | 지연 증가 대비 정확도 이득이 불확실 |

브라우저 스켈레톤 렌더링은 15fps 수준으로 보여줘도 되지만, 서버 판정 입력은 4fps 중심으로 유지하는 편이 안정적입니다.

## 6. 개선 계획

1. 대표 1명 입력 구조를 track_id별 시계열 입력으로 확장합니다.
2. 사람별 `fall_score`, `posture_state`, `occlusion_state`, `emotion_state`를 따로 산출합니다.
3. 동일 사람의 짧은 누락은 1-2초 tail cache로 이어 붙입니다.
4. 화면 알림은 `P{track_id}` 기준으로 표시하고, 동일 이벤트 중복 알림은 사람별 cooldown으로 합칩니다.
5. 1-5명 실제 영상으로 정확도, FPS, RTT, ID switch rate를 재측정합니다.

## 7. 리스크

- 현재 다중 인원 데이터는 합성 타일링 기반 성능 측정이므로, 실제 병실/복도처럼 사람이 겹치는 장면의 ID switch rate는 별도 검증이 필요합니다.
- 5명 이상은 자세 추정 누락과 라벨 뒤바뀜이 급증할 수 있어 카메라 또는 ROI를 나누는 설계가 더 현실적입니다.
- 사람별 낙상 판정 모델 입력이 통합되기 전에는 UI가 5명을 보여줘도 알림 정확도는 대표 인원 중심으로 설명해야 합니다.
