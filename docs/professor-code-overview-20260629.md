# FallAI 사이트 전체 코드 설명

이 문서는 교수님께 프로젝트 코드를 설명하기 위한 비전공자용 정리입니다. 코드의 모든 줄을 해석하는 문서가 아니라, 전체 사이트가 어떤 방들로 나뉘고 각 파일이 어떤 역할을 하는지 이해할 수 있게 만든 지도입니다.

## 1. 프로젝트 한 문장 요약

FallAI는 영상을 올리거나 웹캠을 연결하면 AI가 사람의 자세와 움직임을 분석하고, 낙상 위험과 행동 상태를 화면에 보여주는 웹사이트입니다.

## 2. 사용자가 보는 기능

| 화면 | 사용자가 하는 일 | 코드 위치 |
| --- | --- | --- |
| 메인 대시보드 | 영상 업로드, 웹캠 분석, 결과 확인 | `src/app/page.dashboard/` |
| 모델 관리 | 현재 모델 성능, 학습 진행, 모델 등록/감도 조절 | `src/app/page.models/` |
| 파이프라인 설명 | AI가 어떤 순서로 판단하는지 확인 | `src/app/page.pipeline/` |
| 관리자 분석 설정 | 분석 정책과 알림 설정 확인 | `src/app/page.admin.analysis/` |
| 발표/문서 화면 | 발표자료와 프로젝트 설명 확인 | `src/app/page.presentation/`, `src/app/page.manual/` |
| 로그인/회원/게시판 | 기본 서비스 기능 | `src/app/page.access/`, `src/app/page.members/`, `src/portal/post/` |

## 3. 코드 구조를 건물에 비유하면

| 폴더 | 쉬운 비유 | 실제 역할 |
| --- | --- | --- |
| `src/app/` | 사용자가 들어가는 방 | 화면 UI, 버튼, 카드, 페이지 구성 |
| `src/model/` | 판단하는 두뇌 | 영상 분석, 사용자 관리, 데이터 처리 |
| `src/controller/` | 출입 관리 | 로그인 여부, 관리자 권한 확인 |
| `src/portal/` | 재사용 가능한 부속 건물 | 게시판, 공통 UI, 세션, ORM |
| `scripts/` | 작업 도구함 | 모델 학습, 성능 테스트, 데이터 점검, 보고서 생성 |
| `docs/` | 설명서 보관함 | 운영 상태, 발표자료, 실험 결과, 복구 문서 |
| `storage/`, `outputs/`, `data/` | 창고 | 업로드 영상, 학습 산출물, 분석 결과 |

## 4. 영상 분석이 흘러가는 과정

1. 사용자가 영상을 업로드하거나 웹캠을 켭니다.
2. 브라우저가 영상을 서버로 보냅니다.
3. `page.dashboard/api.py`가 영상을 받습니다.
4. `video_analysis.py`가 영상 프레임에서 사람을 찾고 자세 좌표를 뽑습니다.
5. 낙상 모델과 자세 모델이 각자 점수를 냅니다.
6. 결과를 합쳐 “낙상 위험”, “행동 상태”, “판단 근거”를 만듭니다.
7. 화면은 원본 영상 대신 스켈레톤 중심으로 보여 개인정보 노출을 줄입니다.
8. 결과와 로그는 나중에 확인할 수 있게 저장됩니다.

## 5. AI 모델을 쉽게 설명하면

| 모델 | 쉬운 설명 | 현재 역할 |
| --- | --- | --- |
| RF-Fall | 낙상인지 아닌지 빠르게 판단하는 모델 | 최종 낙상 판단의 중심 |
| XG-Posture | 서기/걷기/뛰기/앉기/눕기 같은 자세를 설명하는 모델 | 낙상 판단의 설명 근거 |
| 가림 보조 모델 | 하체가 가려져도 판단이 무너지지 않게 돕는 모델 | 가림 상황 보완 |
| AI-Hub 82 표정 모델 | 불편/고통 표정 가능성을 보는 보조 모델 | 낙상 이후 상태 추정 보조 |
| AI-Hub 173 상태 모델 | 운전자/상태 데이터를 기반으로 상태를 보는 보조 모델 | 상태 보조 분석 |

## 6. 최근 개선한 내용

- 모델 관리 화면을 일반 사용자도 이해할 수 있게 `상태만 보기`, `모델 등록`, `감도 조절`, `고급 관리`로 분리했습니다.
- 백그라운드 학습이 실제로 돌아가는지 화면에서 확인할 수 있게 학습 현황과 ETA를 표시했습니다.
- 표정 모델은 단순 반복 학습이 아니라 `non_distress`와 `distress`가 헷갈리는 경계 문제를 따로 분석하고 focal loss와 boundary penalty를 적용했습니다.
- 4개 코너 카메라 synthetic simulation을 실행해 처리량과 RTT를 측정했습니다.
- 포트폴리오 사이트에는 교수님용 코드 설명과 서버 복구 가이드를 추가했습니다.

## 7. 4카메라 테스트 결과 요약

단일 영상을 네 개의 코너 카메라처럼 변환한 뒤 실제 YOLO pose 추론을 실행했습니다.

| 조건 | 4카메라 fused recall | pose FPS | 4초 chunk p95 RTT | 판단 |
| --- | ---: | ---: | ---: | --- |
| 320px | 100.0% | 81.35 | 0.839초 | 실시간 기본값으로 적합 |
| 640px | 100.0% | 18.26 | 3.689초 | 가능하지만 여유가 작음 |

정리하면, 4대 카메라 구조는 프로토타입으로 가능하지만 실제 제품 판정에는 실제 4대 동시 촬영 데이터로 ID 유지율과 낙상/행동 정확도를 다시 검증해야 합니다.

## 8. 교수님께 GitHub로 보여드리는 것이 합리적인가?

네, 가장 합리적입니다. 다만 GitHub에는 다음을 구분해서 올리는 것이 좋습니다.

| GitHub에 올려도 좋은 것 | 따로 보관해야 하는 것 |
| --- | --- |
| 소스 코드 | 원본 대용량 영상 |
| README와 설명 문서 | AI-Hub 원본 데이터 |
| 학습/성능 테스트 스크립트 | 개인정보가 포함된 파일 |
| 작은 샘플 이미지와 SVG | 비밀번호, API 키, GitHub 토큰 |
| 결과 요약 보고서 | 학습된 대용량 모델 파일 |

즉, 교수님께는 GitHub 저장소 링크와 배포된 웹사이트 링크를 함께 보내는 것이 좋습니다. 대용량 데이터나 민감 정보는 별도 저장소, 외장 저장장치, 클라우드 드라이브로 분리해야 안전합니다.
